# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

**HotPatata** is a 2–4 player cooperative first-person parkour / hot-potato game: players finish a course while throwing a live bomb between them. Unity **6000.3.25f1** (Unity 6.3 LTS), URP 17.3, Input System 1.20, Windows PC target.

The project has completed **Milestones 1-3 and 5** (M5 = the first full greybox course, `PrototypeCourse`, see `ARCHITECTURE.md` for the beat layout). Milestone 4 (online sessions and lobby) is done and verified with real Relay sessions. The project is linked to Unity Cloud (project HotPatata, org Traziiex) and Relay + Sessions were verified working (a Relay-backed session was created and deleted from the Editor via `MultiplayerService.CreateSessionAsync(new SessionOptions{MaxPlayers=4}.WithRelayNetwork())`, after `UnityServices.InitializeAsync()` and anonymous sign-in); `HotPatata.asmdef` already references the Services assemblies; earlier work: **Milestones 1-3** (M3 = host-authoritative networking proof; its manual gate M3.7, testing on two physical machines, is still open). Earlier: **Milestone 1** (local PassSandbox: movement, bomb hold/throw/catch, fuse, beep, world-contact explosion, fast reset; the human "proof-of-fun" gate M1.11 is being playtested) and **Milestone 2** (reusable greybox prefab kit). Netcode for GameObjects 2.13, Multiplayer Services and Multiplayer Play Mode are installed. Scenes: `Assets/Scenes/Bootstrap.unity` (entry: Host / Join by IP / Play Local, choose Course or Sandbox), `PrototypeCourse.unity` (the course) and `PassSandbox.unity` (one bomb, a `KitDemo` group, no pre-placed players: `PlayerSpawner` builds the offline two-player rig or, on the host, one networked player per connection). `Assets/Scripts/HotPatata.asmdef` holds all gameplay code (namespace `HotPatata`).

## Source-of-truth docs (read before implementing)

- `PROJECT_SPEC.md` is the gameplay source of truth. **If a task conflicts with it, the spec wins.** It defines the non-negotiable rules, bomb state model, tuning starting values, and the explicit out-of-scope list.
- `ARCHITECTURE.md` holds the intended technical structure: scenes, folder layout, component names, authority model, layer policy.
- `MVP_TASKS.md` is the ordered milestone plan (M0 → M8) with acceptance criteria. Work in order and do not skip acceptance criteria.

## Rules that shape all code

- **Do not invent gameplay features.** Out of scope: bounce/ricochet, bomb resting on geometry, floor pickup, multiple bombs, combat, grabbing, matchmaking, etc. (full list in spec §17.2).
- **Local first, then network.** Build and validate the local PassSandbox loop (move, jump, throw, catch, fuse, world-contact explosion, reset) before any networking or level content (`ARCHITECTURE.md` §15, `MVP_TASKS.md` M1.11 gate). Netcode work waits for Milestone 3.
- **Host authoritative, single decision point.** Bomb carrier, catch acceptance, fuse expiry, explosion, checkpoint activation, section reset, and finish are each decided once, on the host. Clients only send input or requests and display replicated state. Catch logic lives only in `CatchResolver`, never duplicated in player scripts.
- **First person.** `FirstPersonCamera` sits at the player's `CameraTarget` (eye pivot); the body always faces `PlayerLook.Yaw`, pitch rotates only the eye pivot. `HandAnchor` and `ThrowOrigin` are children of that pivot so the carrier sees the bomb in hand (no hand models). The followed player's own renderers are `ShadowsOnly` (`PlayerPresentation.SetLocalView`); never hide the held bomb.
- **Charged throw, timed catch.** Hold throw to charge, release to throw (speed `throwSpeedMin`→`throwSpeedMax` over `throwChargeTime`; a tap is the shortest pass). Catching is never automatic: `PlayerCatcher` opens a short window (`catchWindowDuration`) on the catch input, with a cooldown, and `CatchResolver` only accepts a catch while `Catcher.WindowOpen`. Both have UI in `AimReticle`. Tests that expect a catch must make the receiver press catch (`CatchWhenNear`).
- **Level kit conventions.** Prefabs live in `Assets/Prefabs/{Platforms,Obstacles,Gameplay}`. Gameplay-critical motion (`MovingPlatform`, `RotatingObstacle`) is a pure function of `SectionClock.Now` (`RunManager.SectionTime`, restarted on every reset), so it is deterministic and needs no explicit reset. Stateful objects (`FallingPlatform`) implement `IResettable`, which `RunManager` calls on reset. Zones (`Checkpoint`, `FinishZone`, falling-platform trigger) use the stateless `PlayerZone.Collect` overlap query, never Enter/Exit bookkeeping. `PlayerMotor` carries riders via `MovingPlatform.FrameDelta`. `KillZone` fails the section for a player and explodes a bomb; `Checkpoint` activates only when ALL players are inside and supplies the reset spawns and bomb carrier slot.
- **Authority and networking.** All rules run through `NetMode.IsAuthority` (true offline and on the host), so the same classes work in both modes. Remote clients never simulate the bomb: `NetworkBomb` replicates one atomic snapshot and `BombController.ApplyMirror` raises the same events locally. Clients only *request* (`NetworkPlayer.RequestThrow/RequestCatch`); the host validates. Owning clients drive their own movement (owner-authoritative `NetworkTransform`); the host moves them on reset via `TeleportOwner`. `Player.IsLocal` guards anything that must only run on the owning machine. Level motion must derive from `SectionClock` (server time), never `Time.time`, to stay in sync. See `ARCHITECTURE.md` §13.1. Level objects sync from shared time (`SectionClock`, `FallingPlatform`'s replicated trigger time). Teleports must go through `Player.TeleportTo` (which sends a network teleport); never move a player transform directly online.
- **First-person feel.** `PlayerViewFeel` (local, camera-followed player only) computes FOV offset, roll, bob, landing dip and throw/catch punches from movement state; `PlayerLook` applies roll/kick/bob to the eye pivot (so the held bomb moves with the view) and `FirstPersonCamera` applies the FOV. `SpeedEffects` (on the camera) owns a runtime URP `Volume` (vignette, chromatic aberration, lens distortion), a wind loop and footstep/landing sounds. Every effect scales with `GameTuning.viewEffectsStrength` (accessibility, must stay honoured). Movement acceleration is progressive (`startAccelerationMultiplier`). Read `Volume.sharedProfile`, never `.profile` (it clones).
- **Course conventions.** The course is built entirely from kit prefabs by a builder script (Editor API, not hand-placed YAML); to change it, edit the geometry in `PrototypeCourse` (parent `SectionRoot/Course`) or rebuild. `Checkpoint.holdFuseOverride` changes the bomb's hold time from that checkpoint on; `RunManager.Restart()` (host, key R on the results screen) rearms everything. `LaunchPad` launches only the machine that owns the player.
- **Throw and catch feel (PROJECT_SPEC §8.2–9.2).** The bomb launches on the release frame (no animation wait) and flies a plain ballistic arc; nothing steers it after release (soft homing and the magnet were removed on purpose, do not bring them back). `ThrowBallistics` holds the shared arc maths. `AimAssist.TryAssist` (pure, used by the thrower's lock preview) turns the launch direction a few degrees toward a receiver in a small cone at the throw's OWN speed; a throw too weak to reach only gets a heading correction and falls short (the assist never creates range). Forgiveness lives on the receiver: `CatchResolver` sweeps the bomb's path between physics steps against `ReachFor` (`catchRadius` + facing bonus) and allows a short late-press grace. `BombController.IntendedReceiver` (replicated) only drives the "CATCH!" marker. `PlayerCatcher.Hint` explains failed catches ("Too late by N ms" / "Too early"); the debug HUD shows ping (`NetMode.RttMs`). F3 toggles `ThrowDebugOverlay` (raw/assisted aim, cone, arcs, catch reach, last flight) and each throw logs one `[Throw]` line (dev only, `HotPatata.DebugTools`); offline, F4 turns the idle player into a catch/throw-back bot and F5 cycles its movement (PassSandbox has a 4/8/12/16 m lane on its east side). A remote client draws its own throw immediately (`NetworkBomb.PredictLocalThrow`, drawing only). Tests that measure raw throw physics must set `tuning.assistStrength = 0` (restore in `finally`). `PassFeelTests` is the feel regression suite: run it after any throw/catch tuning change.
- **Bomb visual.** The bomb is a potato (`Assets/Art/Models/Bomb/potato.glb`, imported with glTFast; UVs flipped in the copy `Potato_UVfixed.asset`, URP Lit material `Bomb_Potato`). The model is the `Model` child of `Bomb/Visual`; `BombPresentation` drives its `_EmissionColor` pulse, scale pop and cosmetic motion (random-axis tumble in flight scaled by throw speed, gentle sway and a small jolt in the hand: `tumble*`/`handSway*` in `GameTuning`). Rotation is on `Visual` only, never the Rigidbody. To swap the model: replace the mesh/material on `Model` and keep `BombPresentation.bodyRenderer` pointing at its renderer.
- **Bomb state machine is explicit:** `Held → Thrown → CaughtGrace → Held`, plus `Exploding` and `Resetting`. While `Thrown`, contact with any environment collider is an immediate explosion (no bounce). Contact with a valid catch volume is a catch. While `Held`, world contact must never fail the bomb.
- **Collision by layers/markers, never object names.** Planned layers: `Player`, `PlayerCatch`, `Bomb`, `Environment`, `Hazard`, `Trigger`. Any bomb-safe surface needs an explicit marker component or layer.
- **All tuning goes in ScriptableObject(s)** (`GameTuning`, under `Assets/ScriptableObjects/Tuning/`). Do not scatter magic numbers. Starting values are in spec §20.
- **Separation of concerns:** `PlayerMotor` must not know bomb rules. Presentation and audio components (`BombAudio`, `BombPresentation`, `PlayerPresentation`) consume state and never control it.
- **Prefabs:** no Find-by-name runtime lookups or hidden scene-only dependencies. Stateful objects (moving/falling platforms, rotating bars) must support checkpoint reset. Use the Input System (never the legacy input manager).
- **Dependencies:** do not add third-party packages unless the built-in stack clearly can't do the job.

## Working with the Unity Editor

- Prefer Editor/MCP operations (the installed `unity` plugin and its `unity-cli` skill) for creating scenes, GameObjects, prefabs, components and serialized references, and for reading the Console. Hand-editing `.unity` / `.prefab` YAML is a last resort.
- After each change: let Unity compile, check the Console, and fix errors before starting the next task. Never stack features on top of compile errors.
- `Library/`, `Temp/`, `Logs/`, `UserSettings/` are gitignored. Keep `.meta` files with their assets.
- Tests use the Unity Test Framework: EditMode in `Assets/Tests/EditMode/` (config, fuse maths), PlayMode in `Assets/Tests/PlayMode/` (load `PassSandbox`, drive players through `PlayerInputReader.Scripted`). There are no build/lint scripts; everything runs through the Editor. With a live Editor: `unity command run_tests --mode EditMode`, or `--mode PlayMode --async_tests true` then poll `unity command test_status` (results also in `Temp/pipeline_test_status.json`).
- Testing quirks: an unfocused Editor freezes Play Mode unless `Application.runInBackground` is true (the PlayMode base fixture sets it), and hand-simulated key input is unreliable, so tests use `ScriptedInput` and `LocalPlayerSwitcher.SuppressAutoFocus`. Never use the CLI `simulate_key` / `InputTestFixture` against a live Editor: they add virtual Keyboard/Mouse devices that survive domain reloads, and past ~80 of them every action binding fails with `Control count per binding cannot exceed byte.MaxValue=255` (input dead, game unplayable). If it happens, remove the extras with `InputSystem.RemoveDevice` on every device where `!device.native` (check `InputSystem.devices`: expect 1 keyboard, 1 mouse).
- Online sessions: `NetworkBootstrap` (on the persistent NetworkManager prefab) draws the menu and lobby; `SessionService` wraps Multiplayer Services. Extra flags: `-patataHostOnline`, `-patataJoinCode <code>`, `-patataAutoStart <n>` (host starts the level when n players are in), `-patataLeaveAfter <s>`. To drive it from the Editor: `_ = HotPatata.NetworkBootstrap.Instance.HostOnlineAsync();` then read `.SessionCode`, `StartLevel()`, `LeaveAsync(null)`. Never call `NetworkManager.Shutdown` in session mode; a hard-killed client stays listed by the service for a while (the host lobby shows only really-connected players).
- **Latency testing.** `UnityTransport.SetDebugSimulatorParameters` is obsolete and does NOTHING; the M3 "31/31 catches at 100 ms" run was therefore not under latency (corrected). Real simulation uses Unity's Network Simulator (`HotPatata.DebugTools` assembly, Editor / development builds only): `-patataLatency <ms>` or `NetworkBootstrap.Instance.SimulateLatency(ms)` BEFORE hosting/joining, on both sides. Always confirm with `UnityTransport.GetCurrentRtt`. Measured with bots: RTT 5 ms 32/32 catches, RTT 90 ms 26/26, RTT 237 ms 0/16, RTT 386 ms 1/20. Before lag compensation the timed catch broke between ~110 and ~240 ms RTT (240 ms 0/15, all "Too late").
- **Catch lag compensation (M3.5).** A remote client that sees its (late-rendered) bomb reach its catch sphere while its own window is open sends `NetworkPlayer.ClaimCatch`; `CatchResolver.TryResolveCompensatedCatch` accepts it if the host's `FlightHistory` (bomb + every catch centre, recorded each FixedUpdate while Thrown, online only) had the bomb within `catchRadius + 0.4 m` of that player in the last `GameTuning.catchLagCompensation` seconds (0.35 s, also the abuse cap). A lethal contact right after the bomb passed a remote eligible receiver is held (`BombController.ExplosionPending`: still Thrown, frozen) for `min(cap, rtt + 0.15 s)` so the late catch can win. Host "Too late/early" hints for remote players are deferred by the same cap and dropped if the catch lands. Offline and for the host's own player nothing changes. Measured with bots (standalone host + clients, `-patataLatency` both sides): RTT ~230 ms 20/20 (1 client) and 22/22 incl. client→client (2 clients); RTT ~450 ms still 0/14 (beyond the cap; raise `catchLagCompensation` toward 0.5 to cover it, at the cost of longer freezes before explosions).
- **Automated bot sessions without the Editor:** `HotPatata.exe -batchmode -nographics -patataHost -patataBot -patataScene PassSandbox -patataLatency <ms> -patataQuit <s> -logFile host.log` plus N × `-patataJoin 127.0.0.1 -patataBot ...`. Bots pass to the next slot (round robin), so 3+ players exercise client→client passes. Count `Catch accepted` / `Thrown -> Exploding` / `lag-compensated` in the host log.
- Multiplayer smoke test with two processes (no second machine needed): build a Development player (`unity command build --target StandaloneWindows64 --outputPath <abs>/Builds/HotPatata/HotPatata.exe --options '["Development"]' --confirm true`, poll `build_status`), open `Bootstrap` in the Editor, Play, then `eval` `HotPatata.PlayerBot.Enabled = true; HotPatata.NetworkBootstrap.Instance.StartHost();` and launch `HotPatata.exe -batchmode -nographics -patataJoin 127.0.0.1 -patataBot -patataQuit 60 -logFile <abs>/client.log`. Bots pass the bomb back and forth; compare `[Bomb]`/`[Run]` logs on both sides (client lines are tagged `(mirror)`). Flags: `-patataHost`, `-patataJoin <ip>`, `-patataLocal`, `-patataBot`, `-patataQuit <s>`, `-patataLatency <ms>` (dev builds/Editor: `NetworkBootstrap.Instance.SimulateLatency(ms)`). Do not grep logs for "error": `ApplyMirror` contains it.
- `Application.runInBackground` is now **on in the project settings** (a networked game must not freeze when unfocused).
- **CI / releases.** `.github/workflows/build-windows.yml` builds StandaloneWindows64 (Mono) with GameCI on GitHub-hosted Ubuntu. A push to `main` uploads a zipped build artifact; pushing a `v*` tag on a commit that is on `main` (`git tag v0.2.0 && git push origin v0.2.0`) publishes a GitHub Release with `HotPatata-Windows-<version>.zip` (the version comes from the tag). Needs repo secrets `UNITY_LICENSE` (contents of `C:\ProgramData\Unity\Unity_lic.ulf`), `UNITY_EMAIL`, `UNITY_PASSWORD`. Game "beep" (the bomb fuse sound: `beepIntervals`, `BombAudio.Beeped`) is a gameplay term, not the old project name; keep it.
- `run_script`/`eval_file` (unity command) compile a scratch C# file against the project assemblies with no domain reload; handy for building scenes/prefabs via Editor APIs. `eval` snippets cannot use `using` directives.

## Planned layout (partly created, see `ARCHITECTURE.md` §4–5)

- Scenes: `Bootstrap`, `Lobby`, `PassSandbox` (build first), `PrototypeCourse`.
- `Assets/Scripts/` is split into `Core`, `Networking`, `Player`, `Bomb`, `Run`, `Obstacles`, `UI`, `Debug`. Prefabs are grouped as `Player`, `Bomb`, `Gameplay`, `Platforms`, `Obstacles`.
- Runtime systems: `RunManager` (run state, checkpoint, reset order) with `Checkpoint`, `KillZone`, `FinishZone`. The bomb is `BombController` + `BombFuse` + `BombPhysics` + `CatchResolver`. The player is `PlayerMotor` + `PlayerLook` + `PlayerThrower` + `PlayerCatcher` + `PlayerCatchVolume`, viewed through `FirstPersonCamera`.
- Development logs use a concise `[Bomb]` / `[Run]` prefix format that can be switched off (`ARCHITECTURE.md` §19).
